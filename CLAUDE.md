## Resumen del proyecto

**FutbolSim** ("Simulador de Fútbol") es una aplicación web FastAPI que simula un Mundial completo: clasificación de países por confederación a través de múltiples fases, sorteo de grupos, calendario de partidos, simulación realista de partidos (estadísticas a nivel de jugador, tácticas, desgaste, clima, tiros libres, córners, penales, expulsiones), rankings y un dashboard de estadísticas. Sobre ese núcleo de torneo corre una capa completa de "meta-juego"/economía para el usuario logueado: quinielas, mercado de selecciones (comprar/vender países como acciones), fantasy ("Once Ideal"), álbum de estampas coleccionables, inversión en sedes/estadios, misiones diarias + trivia, un "scouter" de pre-partido con probabilidades, popularidad/aficionados por país, y una vista de "Simulación en Vivo" que revela un partido ya simulado minuto a minuto como si fuera en directo. Renderizado en el servidor con Jinja2 + Bootstrap 5 (vía CDN) salvo la vista en vivo, que es 100% client-rendered contra endpoints JSON; MongoDB Atlas es el único datastore realmente en uso.

## Comandos

```bash
# Instalar dependencias (usar el .venv existente o crear uno)
pip install -r requirements.txt

# Levantar el servidor de desarrollo (auto-reload)
uvicorn main:app --reload
```

No hay linter, formatter ni framework de tests configurado (no hay pytest/ruff/flake8/pyproject.toml). `test.py`, `probar_calificaciones.py`, `ajuste_pais_jugador.py`, `asignar_rasgos_jugadores.py`, `configurar_juego_en_vivo.py` y `configurar_roles.py` son scripts sueltos que se ejecutan directamente con `python <archivo>.py` contra la base de datos real (para rellenar datos, volver a procesar fases de clasificación, o asignar rasgos de jugador de una sola vez) — no son una suite de tests automatizada, y varios son de una sola corrida (idempotencia no garantizada, ver comentarios de cada uno antes de repetir la ejecución). No hay paso de build; es una app server-rendered simple.

## Arquitectura

**Capas**: `routes/` (routers de FastAPI, solo HTTP + templating con Jinja2) → `services/` (toda la lógica de negocio y el acceso a MongoDB) → MongoDB (base de datos `mundial`). Las rutas deben mantenerse delgadas: parsear el request, llamar funciones de `services/`, renderizar un template. La lógica de dominio, validaciones y consultas a la base de datos van en `services/`, no en `routes/`.

- `main.py` — crea la app `FastAPI`, monta `/static`, agrega CORS permisivo y `GZipMiddleware` (respuestas > 1 KB: las páginas con listas largas, como la hoja de 1050 árbitros del álbum, bajan ~10x), e incluye ~27 routers de `routes/` (varios módulos exportan un router de API y un `route_vistas` de UI por separado, bajo prefijos distintos).
- `config/settings.py` — prefijos de rutas (`PREFIX_*_PATH`) y configuración desde el entorno / `.env` (plantilla en `.env.example`, `.env` está en `.gitignore`): `MONGODB_URI` (obligatoria: la app no arranca sin ella), `SECRET_KEY` y `COOKIE_SECURE`. En Cloud Run se pasan con `gcloud run deploy ... --set-env-vars` (o `--set-secrets`). Nunca volver a escribir credenciales en el código.

### `routes/` — núcleo del torneo

`simular_route.py` (`/simulador`), `paises_route.py` (`/paises`), `jugadores_route.py` (`/jugadores`), `confederacion_route.py` (`/confederacion`), `juegos_route.py` (`/juegos`), `estadisticas_route.py` (`/estadisticas`), `home_route.py` (sin prefijo, dashboard + `/restart`). `live_match_route.py` (API `/matches`, UI `/en-vivo`) es la "Simulación en Vivo": simula y persiste el partido de una, pero expone el resultado a través de una ventana de revelación progresiva (ver sección de esquema más abajo) — la única vista que no usa Jinja para sus datos, todo llega por `fetch` contra JSON.

Lógica en `services/usuarios_service.py`, con salvaguardas: siempre queda ≥1 admin activo, un admin no se desactiva ni se quita el rol a sí mismo, el rol de sistema `admin` no se borra ni se recorta, un rol con usuarios no se borra.

Reusa la caché de `estadisticas_service` (`_cache_vista`) y tiene la suya con la misma clave. Sistema visual en la sección `mg-*` de styles.css: paleta categórica de 8 en orden fijo (`--s1`…`--s8`, validada contra el fondo `#111c2e`), una serie = `--s1`, cada gráfico con su tabla ("Ver datos").
- `/estadisticas/calendario` ("El calendario del Mundial", `services/calendario_service.py`, enlazada desde /estadisticas y la navegación de Gráficos): estadísticas POR FECHA del Mundial en curso (calendario de calor por día con sus partidos al tocarlo, mes a mes, goles por partido según día de la semana y horario, récords: día más goleador, día con más partidos, jornada más goleadora, racha de días seguidos, primer/último partido) y **efemérides** (`_efemerides`: partidos memorables según `resultado.cronica.historia` con peso por historia —`HISTORIAS`—, hitos de gol 1/100/250/500…, mayor goleada y arranques de confederación/fase, ceses de DT de `dt_cargos` y DT expulsados, eliminaciones; `destacada` = peso ≥ `DESTACADA`). «Un día como hoy» (`un_dia_como_hoy`): "hoy" = fecha del último partido terminado; busca el mismo día del año anterior, si no la misma semana (±3 días), si no lo más pesado de los últimos 30 días. Excluye el partido en transmisión (`_filtro_finalizados`), caché en memoria por (mundial, partidos jugados) (~10 s en frío); la tarjeta «Un día como hoy» del inicio usa `un_dia_como_hoy_inicio()`, que nunca bloquea (si no hay caché la arma en un hilo y esa vez no se muestra). Estilos `cal-*`/`efe-*`/`hoy-card` en styles.css sobre la capa `mg-*`.
- Vistas de análisis agregadas después: `/arbitros` (5 pestañas por puesto, `?puesto=central|linea1|linea2|cuarto|var`) y `/arbitros/perfil?nombre=` (`arbitros_service.py`, sección `arbitros`: `listar_por_puesto` cuenta desde `arbitro_rol` de los eventos —central: faltas/tarjetas/expulsiones/penales/rigor; línea: fueras de lugar y córners; 4to: cambios, revisiones pedidas, minutos añadidos; VAR: revisiones confirmadas/revertidas y goles anulados—, una consulta cacheada por cantidad de partidos; `comparar_con_colegas` compara contra el mismo puesto; los partidos guardan solo el NOMBRE del árbitro y con nombres repetidos en un puesto cuenta el primero), `/ranking` (`ranking_usuarios_service.py`, sección `ranking_usuarios`: patrimonio = saldo + selecciones activas + sedes), `/quinielas/rendimiento` (`quinielas_service.obtener_rendimiento_quinielas`), `/jugadores/comparar` + `/jugadores/api/buscar` (`jugador_analisis_service.py`; los números del comparador salen de los partidos del Mundial activo vía `estadisticas_service._agregar_jugadores_mundial`, no de los contadores de `jugadores`), y secciones dentro de páginas existentes: bitácora de partidos en `/jugadores/{id}` (desde `resultado.participantes`) y trayectoria por Mundial en `/paises/{id}` (`paises_service.obtener_trayectoria_pais`). `/simulador/?id=` de un partido ya jugado redirige al resumen `/juegos/{id}` (una sola vista de partido terminado; el rating por jugador solo existe en `/simulador/simular`, no se persiste). Al sumar una sección nueva al catálogo, los roles YA sembrados no la reciben solos: agregarla a mano en /admin/roles (o con `$addToSet` sobre `roles.permisos`).

`prematch_route.py` y `live_match_route.py` comparten el prefijo de API `/matches` (FastAPI permite varios `APIRouter` bajo el mismo prefijo, se distinguen por `tags` en `/docs`).

### `services/` — núcleo del torneo

- `mundial_service.py` — orquesta un torneo completo: creación de un nuevo Mundial (`crear_nuevo_mundial`), reinicio total (`restart_mundial`, ver esquema de datos), avance a la siguiente fase, agregados para el dashboard.
- `config/eliminatorias.py` — texto del encabezado del inicio por (confederación, fase) y rondas por confederación (`RONDAS_POR_CONFEDERACION`, el "Ronda X de N"); refleja las reglas de `clasificacion_service.py`, si cambia un formato allá hay que actualizar el texto acá.
- `confederacion_service.py`, `clasificacion_service.py` — lógica de clasificación por confederación (`get_confederacion` + `_enriquecer_vista_confederacion` arman la vista `/confederacion/{id}`: tabla de cada grupo ya ordenada con racha de 5 y estado avanzó/en juego/eliminado, avance por ronda, descripción del formato desde `config/eliminatorias.py`, últimos/próximos partidos — una sola consulta de `juegos` con proyección); `clasificacion_service.py` tiene funciones por fase (`procesar_clasificacion_fase_1` … `_7`, más una genérica) ya que el formato de clasificación difiere entre confederaciones, y `obtener_tablas_posiciones_por_grupo`/`obtener_tabla_grupo_de_equipo` (reusadas por `prematch_service.py` y `live_match_service.py`).
- `grupos_service.py` — sorteo de grupos para cada etapa eliminatoria.
- `juegos_service.py` — ciclo de vida del partido: generación de fixtures, `ejecutar_simulacion_completa` (motor + persistencia + efectos secundarios, compartido por `simular_route.py` y `live_match_route.py`), asistencia (`calcular_asistencia`), clima (`generar_clima_partido`). `simular_y_registrar_resultado` genera y guarda clima y aforo si faltan (antes solo se creaban al abrir el detalle previo, así que la mayoría de los partidos se jugaron sin clima y sin aforo: de los primeros 548 solo 23 los tienen).
- `simular_service.py` — el motor de simulación (`simular_partido_realista`): posesión por zona (`defensa`/`medio`/`ataque`) con duelos de atributos vía `resolver_duelo` (probabilidad tipo Elo sesgada por diferencia de atributos), y sub-motores dedicados para penales (`ejecutar_penal` + tanda completa en `simular_tanda_penaltis`), tiros libres directos (`ejecutar_tiro_libre`, cadena muro→a puerta→arquero) y córners (`ejecutar_corner`, cadena disputa aérea→a puerta→arquero) — los tres últimos agregados recientemente, junto con `bonus_pie_habil` (plus de precisión para jugadores `pie_habil == "ambidiestro"`) y bonos de `especialista_penales`/`especialista_tiros_libres` en sus respectivos duelos. **Desgaste físico** (`services/desgaste.py`, lógica pura): cada jugador entra con 100 de energía, que baja con el tiempo jugado (`GASTO_POR_MINUTO`; el arquero igual: su desgaste es de concentración y reflejos) y con cada acción que protagoniza o defiende (`COSTO_ACCION`), frenado por su `resistencia` y acelerado por el clima (`modificadores.desgaste` de `generar_clima_partido`); por debajo de 70 sus atributos rinden menos (hasta 10%, los defensivos hasta 38%: el cansancio abre los partidos; calibrado con Monte Carlo para que los goles por partido no cambien) — los valores sin cansancio quedan en `jugador['_base']` y los atributos del dict del partido se reescriben en el lugar, así todos los duelos lo sienten sin tocar cada fórmula. Los cambios priorizan a los más cansados (`desgaste.peso_para_salir`), la probabilidad de cambio sube con el cansancio (`PROB_CAMBIO_BASE`/`PROB_CAMBIO_POR_CANSANCIO`/`UMBRAL_CAMBIO_ENERGIA`) y el que entra llega fresco; al cruzar 30 de energía se narra un evento `🥵 DESGASTE`; `stats_jugadores[id].energia_final`. **Cuerpo arbitral y reloj** (`services/arbitraje.py`, lógica pura): `obtener_cuarteta_arbitral(excluir_paises)` sortea 5 árbitros (central, `linea1`, `linea2`, `cuarto`, `var`) de países neutrales y devuelve el `rigor` del central (`arbitros.rigor`, permanente, `asignar_rigor_arbitros.py`; multiplica la probabilidad de tarjeta y, al 30%, la de falta). Jueces de línea por lado (`rol_juez_de_linea`: en el 1T `linea1` cubre donde ataca el local, en el 2T se invierten): marcan `🚩 FUERA DE LUGAR` y `🚩 SAQUE DE ESQUINA`. El 4to anuncia cambios, levanta el cartel `⏱️ TIEMPO AÑADIDO` (`calcular_anadido` según las paradas del periodo; se juega ese descuento) y PIDE la revisión `🖥️ REVISIÓN VAR`; el VAR decide `🖥️ VAR - CONFIRMADO` o revierte (`GOL ANULADO`/`TARJETA REVISADA`/`PENAL ANULADO`/`ROJA DIRECTA`), con `PROB_REVISION × PROB_REVIERTE` = la misma tasa de anulación de antes. Cada VAR tiene personalidad permanente (`asignar_perfil_var.py`): `arbitros.var_intervencion` (×0.45–1.8 a la probabilidad de revisar: "deja correr" / "equilibrado" / "intervencionista") y `var_severidad` (×0.6–1.4 a la de revertir: "respeta al campo" / "ecuánime" / "implacable"), independientes y con promedio 1 (la tasa de anulación del torneo no cambia); `obtener_cuarteta_arbitral` los devuelve como `perfil_var` y viajan hasta `ejecutar_penal`/`simular_tanda_penaltis`; se ven en /arbitros y en la crónica. Penales en juego (`PROB_PENAL_FALTA_ATAQUE`, ~0,2 por partido): el gol se registra como `⚽ GOL` con `de_penal: true` (así lo cuentan marcador, estadísticas y Juego en Vivo; `⚽ GOL DE PENAL` es SOLO de la tanda). `segundos_acumulados` es la línea de tiempo continua (incluye descuentos); al final `aplicar_reloj` pone en cada evento `periodo` (1, 2, 3-4 alargue, 5 tanda), `minuto` (topado en 45/90/105/120 en el descuento) y `adicional`, y `asignar_arbitros` agrega `arbitro`/`arbitro_rol` (y `var_decision`). Mostrar con `minuto_texto` / "90+3'" (resumen, `live_match.js` `minutoTexto`, `adicional_actual` del payload en vivo); los partidos viejos no traen esos campos y se ven como antes. Calibrado con Monte Carlo para no mover goles/tarjetas por partido (`BASE_GOL_REMATE`, `AJUSTE_TARJETAS_DESCUENTO`, `AJUSTE_FALTAS_DESCUENTO`; fuera de lugar realista `PROB_FUERA_DE_LUGAR` ~4,4 por partido —antes ~20—). Los partidos jugados antes de esto se ajustaron con `asignar_arbitros_partidos.py` (`--muestra`/`--aplicar`/`--revertir`, respaldo en `respaldos/`): `arbitros.var` sorteado por partido, `arbitro`/`arbitro_rol` en sus eventos (córner viejo = el `🖐️ DESVÍO A CÓRNER`, revisión pedida = `var_pedido_por` en la decisión del VAR), sin agregar ni quitar eventos. También modela tarjetas/expulsiones (`procesar_expulsion`, saca al jugador de `plantilla` en tiempo real y lo excluye de la posesión inmediatamente), sustituciones (`realizar_sustitucion`), clima/árbitros y alargue + penales para series ida-vuelta.
- `paises_service.py` / `international_service.py` — datos de países, poder y ranking (`actualizar_poder_y_rankin`, `recalcular_rankin`).
- `jugadores_service.py` — `actualizar_jugadores_post_partido` es el único punto que persiste stats de partido en la colección `jugadores` (ver "Esquema de datos" para la lista completa de campos `$inc`).
- `ciudades_service.py`, `fecha_service.py`, `estadisticas_service.py` — ciudades sede, calendario y agregación de estadísticas para el dashboard (**todo del Mundial en curso**: `_filtro_finalizados()` agrega `mundial_id` activo y excluye el partido en transmisión a todas las consultas; `obtener_estadisticas_generales` carga una sola vez los partidos con proyección (`_juegos_del_mundial`), arma por jugador `_agregar_jugadores_mundial` (goles/atajadas/participantes del resultado + asistencias, tarjetas, faltas, recuperaciones, regates y disparos desde los eventos, resolviendo nombre→id por (país, nombre); los contadores de `jugadores` NO sirven porque no se reinician entre mundiales) y por selección `_agregar_paises_mundial`, de ahí salen los líderes y los top 10 (`TOP_JUGADORES`/`TOP_SELECCIONES`); el resultado se cachea en memoria con clave (mundial, cantidad de partidos jugados), así solo se recalcula cuando termina un partido; `GET /estadisticas/api/detalle?tipo=jugador|seleccion&id=&metrica=` (`obtener_detalle_estadistica`) da los partidos donde sumó cada uno para el modal; `estadisticas_service.py` ya tiene ~15 líderes distintos, más récords por partido derivados de `resultado.eventos` — árbitro central con más/menos faltas y tarjetas EN UN partido (no promedio: cada central dirige 1-4 partidos), primer gol más rápido/tardío, sede más goleadora — y un bloque de tendencias del torneo (goles/partido, ambos marcan, localía, goles por franja, mayor goleada, hat-tricks), todo desde una sola consulta con proyección (`_juegos_finalizados_para_records`); varios requieren recorrer `juegos.resultado.goleadores[]`/`eventos[]` de todo el torneo en vez de un simple `find_one` sobre `jugadores`, ver esquema).
- `cronica_service.py` — **crónica de cada partido** escrita desde la CRONOLOGÍA (`resultado.eventos`), no solo el marcador: `analizar` lee el partido en orden (cada gol con su contexto —abre, empata, pone adelante, da vuelta, amplía, sentencia, descuenta—, rojas, VAR, atajadas por arquero, ingresos de leyendas, desgaste, alargue y tanda) y detecta las HISTORIAS con prioridad (remontada/remontada épica, rescate, gol agónico, goleada/paliza, hat-trick/doblete, sorpresa por ranking, aguantar con diez, arquero figura, leyenda decisiva, cambio que definió, penales...); `redactar` arma la nota en tono mixto diario/radio: titular, entrada (estadio, competencia, público, clima, leyendas titulares), primer tiempo, segundo tiempo y alargue/penales como línea de tiempo por segundos de juego, figura y números, y qué significa (en eliminación directa, quién avanza o es campeón), más el post corto del feed. Plantillas con varias variantes por bloque y semilla = id del partido (el mismo partido siempre igual). Involucra al cuerpo arbitral (central con su rigor en la entrada, quién cobró cada penal y mostró cada roja, el VAR que confirma o anula —historia `var_decisivo` si un gol anulado cambió el resultado—, el 4to árbitro en los goles del descuento; en partidos sin `arbitros.var` dice "el central, tras consultar el VAR"). Se guarda en `resultado.cronica = {version, titular, parrafos, post, historia, resaltar, generada_en}` (`resaltar` = jugadores/árbitros/equipos del partido: la vista los resalta con el filtro `resaltar_cronica` de `juegos_service`, clases `cronica-jugador/-arbitro/-equipo`) SIN tocar los textos viejos (`opinion`, `texto_narrativo`); `asegurar_cronica` la escribe al terminar el partido (gancho al final de `juegos_service.aplicar_efectos_secundarios`) o al abrir `/juegos/{id}` si falta o es de una `VERSION` anterior (subir `VERSION` las reescribe todas al consultarlas), nunca durante una transmisión en vivo; `generar_cronicas.py` (`--forzar`, `--muestra N`) las escribe de una vez. El feed del inicio usa `cronica.post` si existe. `actualizar_jugadores_reales.py` pone `cronica` en null al renombrar (se reescribe sola con los nombres nuevos).
- `probabilidades_service.py` — **probabilidades de cada selección** (clasificar al Mundial, dieciseisavos, octavos, cuartos, semis, final, campeón; ACUMULADAS), en la ficha `/paises/{id}`. Monte Carlo (`ITERACIONES` = 3000, ~25 ms por torneo) del RESTO del torneo desde el estado real (`internacional` = vivos; tablas y partidos pendientes de la fase en curso de cada confederación), con el reglamento de `clasificacion_service` codificado en `REGLAS` (posiciones → Mundial/repechaje/siguiente fase, "mejores N de la posición P"), fases futuras sorteadas como `grupos_service.asignar_grupos_fase` (cantidad de grupos en `GRUPOS_FASE`), llaves ida y vuelta, repechaje, regla del anfitrión, sorteo del Mundial por bombos con restricciones por confederación, 8 mejores terceros, dieciseisavos y llaves con alargue/penales. **Modelo de partido** (elegido con los datos): goles Poisson independientes (var ≈ media, r = 0,03, sin localía), λ = μ·ataque(A)·defensa(B) con contracción `K_CONTRACCION` = 20 partidos virtuales (mejor log-loss fuera de muestra; backtest sobre AFC fase 2: Brier 0,126 vs 0,250 sin información, bien calibrado). NO usa overall ni 'poder': en el motor la plantilla casi no mueve goles (pendiente 0,01 ± 0,03 en 3.600 partidos simulados) y el overall actual está contaminado por los resultados (ganar sube moral/forma/rendimiento). Si cambia el reglamento de una eliminatoria, actualizar `REGLAS`/`GRUPOS_FASE`. Persistencia: una corrida por cantidad de partidos jugados (sin el que se transmite) en `probabilidades_mundial` (historia → gráfico de evolución); se recalcula en un PROCESO aparte (`python -m services.probabilidades_service --recalcular`, candado en `probabilidades_candado`) al terminar cada partido (gancho en `aplicar_efectos_secundarios`) o al abrir una ficha desactualizada; `restart_mundial` borra ambas colecciones. ⚠️ En Cloud Run un proceso lanzado después de la respuesta puede quedar sin CPU: allí conviene correrlo como job.
- `tecnicos.py` (lógica pura) + `tecnicos_service.py` — **Directores técnicos**: 5 por selección en `directores_tecnicos` (PERMANENTE; `agregar_tecnicos.py --descargar/--muestra/--aplicar/--revertir`: técnicos reales de Wikidata de la nacionalidad del país —ocupación entrenador, vivos, 35-75 años—, sin nadie que ya esté en el sistema como jugador, leyenda o árbitro; los países chicos se completan con inventados `ficticio: true`), avatares de traje (`generar_avatares_tecnicos.py`, bucket `tecnicos/<id>.svg`, `img_tecnico`/`m.avatar_tecnico`). Rasgos 0..100 centrados en 55: `estilo` (táctica preferida), `lectura` (ajuste táctico en vivo), `motivacion` (+ efecto técnico nuevo en sus 3 primeros partidos), `temperamento` (reclamos), `confianza_leyendas`. En el motor (`simular_service`): el DT elige la táctica y cuántas leyendas arrancan, y `tecnicos.Banco` aplica sus efectos como `jugador["_ajuste"]` = {general, ataque, defensa} que `desgaste._refrescar` suma después del cansancio; eventos `📋 AJUSTE TÁCTICO`, `🗣️ RECLAMO DEL DT`, `🟨 DT AMONESTADO`, `🟥 DT EXPULSADO` (nombres SIN "AMARILLA"/"ROJA"/"TARJETA" a propósito: hay consumidores que cuentan tarjetas por substring); `resultado.dt.{local,visita}`. Calibrado con Monte Carlo (+4 de atributos = +11 puntos de prob. de ganar; el DT mueve <1): goles/tarjetas del torneo sin cambio, DT expulsado ~1 cada 17 partidos, mejor vs peor DT ~3-5 puntos. Sin `paises.dt_id` el partido se juega como antes. **Federación**: `registrar_partido` (gancho al final de `aplicar_efectos_secundarios`, diferido en vivo, idempotente por juego) suma el resultado al cargo vigente (`dt_cargos`, permanente) y decide el cese con `decidir_cese` (presión = media móvil de puntos esperados por prestigio −aficionados− menos obtenidos, golpes por goleada/expulsión, paciencia `paises.federacion_paciencia`, mínimo 3 partidos, eliminación = evaluación única); `elegir_reemplazo` entre los otros 4 (un cesado reciente puede volver, poco probable). Todo determinístico (semilla = juego + país). `asignar_tecnicos_partidos.py` reconstruyó la historia desde el primer partido con las mismas funciones (sin tocar eventos ni marcadores). `crear_nuevo_mundial` llama `asegurar_dt_en_todos`; `restart_mundial` no toca nada de esto. Vistas: `/tecnicos/` (destacados, «cuerda floja» = más `prob_cese`, «intocables» = más puntos sobre lo esperado, relevos con fecha y récord, tarjetas con arquetipo/rasgos/riesgo) y `/tecnicos/{id}` (`arquetipo(t)` = rol + estilo + temple, radar de rasgos con percentiles, puntos reales vs esperados partido a partido, cargos con fechas, bitácora; estilos `tc-*` en styles.css) (sección `tecnicos`), tarjeta «Cuerpo técnico» en `/paises/{id}`, DT en alineaciones del resumen, `m.chip_dt` en Scouter y detalle previo, avisos de relevo en el feed del inicio y en el resumen del partido que lo provocó (`ceses_del_partido`: quién se va con su récord, quién asume), historias `ajuste_decisivo`/`dt_expulsado` en la crónica.
- `live_match_service.py` — motor de la "Simulación en Vivo": simula y persiste el partido de una, pero lo expone a través de una máquina de estados `juegos.transmision` (`in_progress`/`finished`) que revela `resultado.eventos` progresivamente según el tiempo transcurrido real. Los efectos secundarios (país, jugadores, rankings, aficionados, quinielas, ownership, fantasy, sedes, avance de fase) quedan diferidos en `juegos.efectos_pendientes` hasta que la ventana termina, para no spoilear standings/perfiles antes de tiempo — `obtener_estado_live` hace un "auto-finalize-on-read" con update condicional atómico sobre `transmision.estado`, así que aunque varios clientes hagan polling a la vez los efectos se disparan exactamente una vez. Cada transmisión dura `DURACION_TRANSMISION_SEGUNDOS` = 1500 (25 min; ~310 eventos revelados de a uno, ~4,8 s cada uno —4,3 a 5,4 según el partido—; con el ritmo de 30 min quedan 5 de pausa; la duración queda guardada en `transmision.duracion_segundos` de cada partido).
- `pulso_service.py` — **el pulso: el torneo avanza solo en el SERVIDOR** (la reproducción automática ya no vive en `localStorage`). Cloud Scheduler llama cada minuto a `POST /tareas/pulso` (`routes/tareas_route.py`, sin sesión, cabecera `X-Pulso-Clave` = `PULSO_CLAVE` del entorno; sin clave configurada responde 503). `pulsar(fuente)`: candado en Mongo (`pulso.estado`, `CANDADO_SEGUNDOS`), 1) `obtener_estado_live()` cierra la transmisión vencida y aplica sus efectos, 2) si `pulso.config.activo` y no hay transmisión, arranca el siguiente con `iniciar_simulacion_automatica` cuando llega `calcular_proximo_inicio` (grilla fija: inicio anterior + `intervalo_min` —`INTERVALOS_PERMITIDOS` 30/45/60/90/120, 30 por defecto—, nunca antes del fin de la transmisión + `MARGEN_SEGUNDOS`), 3) en Cloud Run (`EN_CLOUD_RUN` = existe `K_SERVICE`) y solo desde el Scheduler recalcula las probabilidades dentro del pedido (~45 s): allí `recalcular_en_segundo_plano` no lanza el proceso aparte porque se quedaría sin CPU. `?simulacro=true` decide sin tocar nada. Respaldos que respetan la misma grilla: `PULSO_LOCAL=1` (hilo cada 30 s en la app, para desarrollo; local y producción comparten la base y el candado evita choques) y el navegador de quien tiene `simular_partidos` (`POST /matches/pulso/tick`, desde `base.html` cada minuto sin transmisión y desde `/en-vivo` al llegar la hora). `GET /matches/pulso` (público: activo, ritmo, `proximo_inicio`; con permiso, además el último pulso y error) y `POST /matches/pulso/config` (interruptor y selector de ritmo de `/en-vivo`, `live_match.js`; aviso `#autoPlayEstado` con la cuenta regresiva para todos). Al no quedar partidos pendientes responde `sin_partidos`; crear el Mundial siguiente sigue siendo manual. Colección `pulso` PERMANENTE.

Cada módulo de meta-juego tiene su(s) propio(s) template(s) (`album_coleccion.html`, `album_sobres.html`, `directorio_sedes.html`, `fantasy_once_ideal.html`, `cuenta.html`, etc.), siguiendo el mismo patrón de cards oscuras con badges de colores. `live_match.html` es la excepción: no recibe datos del servidor, todo el estado (marcador parcial, cronología, tabla de grupo animada, gráfico de "momentum" con Chart.js) se arma en el cliente vía polling a `/matches/live` y `/matches/live/tabla-grupo`.
- `collections/paises.json` — datos semilla estáticos (listado de países con banderas) usados por scripts sueltos para rellenar la colección `paises` en Mongo.

## Esquema de datos (MongoDB, base `mundial`)

La base tiene ~25 colecciones. Núcleo del torneo:

- **`paises`** (211 docs) — roster maestro y permanente de selecciones (nombre, confederación, `estadisticas` anidadas, `rankin`, `poder`, `aficionados`). Además de esto persiste `user_id` (0/`"0"`/`None` = sin dueño, ver `ownership_service.py`) para el mercado de selecciones. Persiste entre mundiales.
- **`internacional`** (197 docs) — snapshot de un país **para el mundial activo**: mismos campos que `paises` más `mundial_id`, `fase_eliminatoria`, `grupo`, `idx_grupo`, `eliminado`.
- **`historial`** (28 docs) — mismo shape que `internacional`; archivo de instancias de mundial ya finalizadas.
- **`grupos`** (9 docs) — snapshot de cada grupo al momento del sorteo. ⚠️ Los países acá guardan las estadísticas **planas** (`puntos`, `jj`, `jg`, `je`, `jp`, `gf`, `gc` directo en el doc) en vez de anidadas bajo `estadisticas` como en `paises`/`internacional`.
- **`juegos`** (878+ docs) — un partido: `equipo_local`/`equipo_visitante`, `ubicacion`, `estadisticas.{local,visitante}` (incluye `tiros_totales` por lado, agregado para la efectividad de gol real por país), y `resultado` (goles, árbitros, `eventos[]`, `opinion`, `ganador_id`/`ganador_lado`/`empate`) que solo existe una vez simulado. `resultado.goleadores[]` es la lista estructurada de quién anotó, con flags adicionales por entrada: `entro_de_cambio` (Súper Sub), `equipo`, `goles_penal`/`goles_tiro_libre`/`goles_corner` (para "Especialista a Balón Parado" — desglosan de qué tipo de jugada vino cada gol; **no** se acumulan en `jugadores`, solo viven acá, así se resetean solos en cada `restart_mundial`). `resultado.atajadores[]`/`resultado.participantes[]` análogos, para racha de goles y modal de "ver partidos". `aforo`/`clima` se agregan post-simulación. `transmision` (`estado: in_progress/finished`, `started_at`, `duracion_segundos`) y `efectos_pendientes` son campos aditivos que solo existen si el partido pasó por el flujo de "Simulación en Vivo" (ver `live_match_service.py`).
- **`jugadores`** (~6963 docs; **33 por selección: 22 actuales —2 por cada una de las 11 posiciones— + 11 LEYENDAS**) — `nombre`/`edad` actualizados con futbolistas reales en actividad por `actualizar_jugadores_reales.py` (Wikipedia: plantel actual + convocatorias recientes, posición exacta de la ficha de cada jugador; `--descargar`/`--muestra`/`--aplicar`/`--revertir`, y `--renombrar "id=Nombre:edad"` para cambios puntuales a mano por el mismo camino; respaldo en `respaldos/`). ⚠️ El NOMBRE del jugador también vive en los partidos jugados (`resultado.eventos[].jugadores`/`descripcion`, `goleadores`/`atajadores[].jugador_nombre`, `comentarios_jugadores`, `titulares_*`, `opinion`, `texto_narrativo`) y en `fantasy_points_history.jugador_nombre`, y Estadísticas vincula eventos por (país, nombre): si renombrás jugadores, reescribí también esas referencias (el script lo hace) o el Mundial en curso pierde sus números. Atributos de simulación (`overall`, `precision_tiro`, `regate`, etc.) y contadores de carrera **por torneo** (se resetean en cada `restart_mundial`, no son acumulado histórico — pese a lo que sugeriría el nombre; el código documenta explícitamente que los campos `_temp` que alguna vez existieron para separar "este torneo" de "histórico" fueron eliminados por no usarse). Contadores actuales, todos `$inc`-eados en `jugadores_service.actualizar_jugadores_post_partido`: `goles`, `asistencias`, `atajadas`, `faltas`, `amarilla`, `roja`, `tiros_puerta`, `tiros_desviados`, `faltas_recibidas` (faltas RECIBIDAS, distinto de `faltas` cometidas), `recuperaciones`, `atajadas_penales` (subconjunto de `atajadas`, específicamente en penales), `juegos_jugados`. Campos **permanentes** (ya NO se resetean en restart, ver `mundial_service.py::restart_mundial`, asignados una sola vez por `asignar_rasgos_jugadores.py`): `pie_habil` (`"derecho"`/`"izquierdo"`/`"ambidiestro"`, distribución ~78/18/4%, afecta duelos de tiro vía `bonus_pie_habil` en `simular_service.py`) y `especialista_penales`/`especialista_tiros_libres` (booleans, ~55% de los equipos tiene uno marcado por rol, dan un bono de precisión en sus respectivos duelos y prioridad para cobrar). **Leyendas** (`leyenda: true`, `agregar_leyendas.py` `--descargar`/`--muestra`/`--aplicar`/`--revertir`; once histórico de retirados por país desde Wikidata + fichas de Wikipedia + `leyendas_curadas.json`; ids desde 4643, dorsales 23-33, edad de plenitud, atributos 80 parejo para todos los países —paridad—, `atributos_base` (lo que restaura `restart_mundial` en vez de 60), `fama` 0..1 (percentil entre leyendas, para el precio), `wikis` (cantidad de Wikipedias con artículo) y `wikidata`; 65 son FICTICIAS —`ficticia: true`, `inspirado_en`, de `leyendas_inventadas.json`— para completar el once de selecciones chicas sin suficientes futbolistas históricos): en cancha máximo 3 por equipo y 1 por línea/sector (lógica pura en `services/reglas_leyendas.py`, aplicada en `simular_service.seleccionar_plantilla_titular` —el DT sortea cuántas arrancan (0 a 3, misma probabilidad) y en qué líneas— y en `realizar_sustitucion`, donde una leyenda expulsada sigue ocupando cupo); evolucionan partido a partido como cualquiera. ⚠️ Cualquier código que lea `jugadores` tiene que decidir si incluye leyendas: el álbum las tiene como categoría propia `LEYENDA` (5%, guardadas en el mismo `owned_jugadores`, sección aparte en la página del país que también cuenta para completarla), corporativos las valúa con escala propia (`corporativo_reglas.valores_con_leyendas`: el percentil de los actuales se calcula SIN ellas) y arrancan libres (la siembra las excluye; la IA tiene tope `MAX_LEYENDAS_IA_POR_CORP` y menos peso), fantasy permite `MAX_LEYENDAS_FANTASY` = 1, las "figuras" de `/paises/{id}` y el `once_ideal` de estadísticas las excluyen (hay `once_leyendas` aparte) y `actualizar_jugadores_reales.py` no las toca. Macro `m.insignia_leyenda()`. ⚠️ Sigue teniendo el par redundante `control_balón` (con tilde, huérfano/muerto) vs `control_balon` (sin tilde, el que se lee de verdad) — verificar cuál usa cada función antes de tocarlo.
- **Juego en Vivo**: `match_live_sessions` (una por usuario+partido, índice único; `estado` pendiente/en_curso/eliminada/finalizada/cancelada, `multiplicador_historial[]` con `efectivo_desde`), `point_transactions` (EVENTO por regla disparada + ENTRADA/PAGO_FINAL/REEMBOLSO de `monto`; índice único `(sesion_id, evento_idx, regla_codigo)` = un evento nunca se procesa dos veces) y `event_point_rules` (reglas editables; si está vacía se usan las de `config/juego_en_vivo.py`). Índices y reglas se crean con `python configurar_juego_en_vivo.py` (idempotente).
- **`mundiales`** (1 doc activo) — el torneo activo (`pais_id`, `anio`, `activo`). Campos de bracket final (`campeon`, `por`, `dfi`, `dfd`, `li`, `ld`, `mi`, `mc`, `md`, `ei`, `dc`, `ed`) siguen en `NoneType`, sin usar.
- **`confederaciones`** (8), **`fases`** (13 — fases 1-6 clasificatorias por confederación, 7 fase de grupos del Mundial, 8-13 eliminación directa a partido único, ver `prematch_service.py`), **`ciudades`** (4246, sede/estadio por país, más `owner_user_id` para el mercado de sedes), **`arbitros`** (1050: 210 por puesto —central, línea 1, línea 2, 4to y **VAR** (5to árbitro, agregados por `agregar_arbitros_var.py` desde `arbitros_var.json`: nombres inventados, uno por país, `origen: "var_generado"`, `--revertir` los borra)—; Islas Feroe no tiene árbitros), **`posiciones`** (11 posiciones granulares reales — Portero + 10 de campo con siglas propias, distinto del esquema simplificado 1-4 `Portero/Defensa/Medio/Delantero` que usa `simular_service.py` internamente vía `linea_partido`; **no asumir que `jugadores.posicion_id` es 1-4**, es el esquema granular) — catálogos de apoyo.
- **`dos_equipos`…`diez_equipos`** — tablas de fixture-template que mapean qué posición de grupo enfrenta a cuál en cada jornada, según el tamaño del grupo.
- **`usuarios`** — cuenta del jugador humano (`monto` = saldo gastable, hasheo bcrypt, `rol` = código de la colección `roles`, `debe_cambiar_password`, `activo` = interruptor de acceso). **`roles`** — `{codigo (único), nombre, descripcion, permisos: [códigos de config/secciones.py] o ["*"], es_sistema}`; se siembran con `python configurar_roles.py` (idempotente; `--password-admin` fija la contraseña de `dummy`, el admin inicial). `restart_mundial` solo resetea `monto`, no toca roles. Todo el resto de colecciones de meta-juego cuelgan de `usuarios` vía `user_id`/`ObjectId`: `user_albums` (`owned_jugadores`/`owned_paises`/`owned_ciudades`/`owned_arbitros`, listas de `id` numérico; `arbitros.id` es PERMANENTE, asignado por `asignar_id_arbitros.py`, índice único en `crear_indices.py`), `pack_purchases` (álbum); `team_ownerships`, `ownership_transactions` (selecciones); `city_ownerships`, `city_revenue_history` (sedes); `fantasy_teams`, `fantasy_points_history`, `album_passive_rewards` (fantasy); `quiniela_config`, `quiniela_usuario` (quinielas); `user_daily_rewards`, `reward_transactions`, `trivia_history` (misiones/trivia); `historial_aficionados` (aficionados); `match_live_sessions`, `point_transactions` (Juego en Vivo); `xp_eventos`, `recompensas_nivel` (niveles, permanentes).

Esquema completo por colección (todos los campos y tipos) relevado con `ver_esquema.py` (script de solo lectura, no forma parte del flujo de la app).

## Convenciones y patrones

- **Idioma de la interfaz**: todo texto visible para el usuario va en español de Latinoamérica (México) con «tú» (tienes, puedes, elige, revisa, aquí), NUNCA voseo rioplatense (tenés, podés, elegí, revisá, acá, vos). Se convirtió todo el sistema una vez (templates, JS, services, routes, config); los textos ya guardados en Mongo (avisos, ofertas viejas) pueden seguir en voseo.
- **Vocabulario de dominio en español** en todo el proyecto (routes, services, variables, templates): `pais`/`paises`, `juego`/`partido`, `fase`, `confederacion`, `mundial`, `clasificacion`, `rankin` (ranking/poder), `plantilla` (squad). Mantené el código nuevo consistente con este vocabulario — no mezclar términos de dominio en inglés.
- **Sinergia del Álbum de Estampas**: patrón repetido en `ownership_service.py`, `venue_service.py` y `fantasy_service.py` — cada uno consulta `user_albums.owned_paises`/`owned_ciudades`/`owned_jugadores` en su propio punto de pago único (`_abonar_puntos_dueno`, `process_match_city_revenue`, `procesar_eventos_jugadores_partido`) para: (a) multiplicar ×1.5 el pago al dueño/titular si además tiene la estampa correspondiente, y (b) dar un bono pasivo fijo (+20 pts, o 20% en fantasy) a cualquier OTRO usuario que tenga esa estampa, sin ser el dueño. Cada módulo deja su propia marca de auditoría (`album_synergy_applied`, `sinergia_album_aplicada`, `type == "SINERGIA_ALBUM"`) en su colección de transacciones — `album_service.py` solo LEE esas marcas para la vista de colección, nunca calcula sinergia por sí mismo. Si agregás un módulo nuevo con estampas de por medio, seguí este mismo patrón en vez de centralizarlo en `album_service.py`.
- **Efectos diferidos + revelación progresiva** (`live_match_service.py`): cuando un partido se simula vía "Simulación en Vivo", el resultado se persiste al instante pero los efectos secundarios (stats de país/jugador, rankings, dividendos, sinergias, avance de fase) quedan guardados en `juegos.efectos_pendientes` y NO se aplican hasta que termina la ventana de revelación — evita que el dashboard/perfiles spoileen el resultado antes de tiempo. Si agregás un efecto secundario nuevo a `ejecutar_simulacion_completa`, verificá si también necesita pasar por este mecanismo de diferido.
- **Conexión a la base de datos por módulo**: la mayoría de los archivos en `services/*.py` instancian su propio `MongoClient` / `db = client.get_database('mundial')` a nivel de módulo (algunos importando `MONGODB_URI` desde `config.settings`, otros redeclarando la URI inline) en lugar de compartir un único cliente. Seguí el patrón existente por archivo salvo que se pida explícitamente refactorizarlo.
- **Convención ruta → service**: las rutas arman un diccionario de contexto para Jinja y retornan `templates.TemplateResponse(request=request, name="<template>.html", context={...})`; cada módulo de rutas define su propio router (`route`, y a veces `route_vistas` separado para las páginas HTML bajo otro prefijo), un `tag` a nivel de módulo, y su propio `logging.basicConfig`/`logger`.
- **Roles y secciones**: cada vista/acción es un código de `config/secciones.py`. Al agregar una vista nueva: sumá su código (y su URL en `URL_SECCION`), protegé su router en `main.py` con `dependencies=_permiso("codigo")`, y mostrá su link en `base.html` con `{% if puede('codigo') %}` (y `nav_activo(...)` para el resaltado). Las acciones sensibles (simular, reiniciar) llevan además `Depends(requiere_permiso(...))` en la propia ruta y sus botones se ocultan con `puede(...)`. Los endpoints de escritura usan SIEMPRE el usuario de la sesión, nunca un `usuario_id` del body.
- **Frontend compartido**: `static/js/ui.js` (cargado en `base.html`) expone `UI.escapar` (usarlo SIEMPRE al meter datos en `innerHTML`), `UI.confirmar({...})` (modal propio; no usar `confirm()` nativo), `UI.refrescarSaldo()` (actualiza la pill de saldo del navbar tras una compra/venta, vía `GET /cuenta/saldo`), `UI.paginador({...})` ("Mostrar más" para listas largas renderizadas en el servidor), `UI.cargando(promesa)` y hace accesibles por teclado los elementos `role="button"`. **Indicadores de carga globales** (también en `ui.js`, sin tocar cada vista): barra de progreso arriba al hacer clic en un link interno o enviar un formulario (salvo que su handler haga `preventDefault`, o con `data-sin-cargador`), aviso "Abriendo …" con una pelota si la navegación pasa de 700 ms, y barra en todo `fetch` que tarde más de 400 ms; los polls periódicos están excluidos en `SIN_CARGADOR` (si agregás un poll nuevo, sumalo ahí). **Login animado**: `templates/login.html` envía con fetch y cabecera `X-Login-Ajax: 1` (`auth_route.login_submit` responde JSON y setea la misma cookie); acierto = animación de gol y después navega, error = atajada + mensaje; sin JavaScript o con `prefers-reduced-motion` funciona sin animación. **Gráficos y animaciones de las fichas** (`static/js/graficos_fifav.js`, en `/paises/{id}` y `/jugadores/{id}`): dentro de un contenedor `.js-animar`, cuando entran en pantalla, los `.anillo-kpi` se llenan y cuentan, las barras de atributos crecen escalonadas, `.barra-wdl` se despliega y los `[data-contar]` cuentan desde 0; `GraficosFIFAV` da el estilo común de Chart.js (tooltip oscuro, brillo `dataset.brillo`, `degradado`, `animacionProgresiva` = la línea se dibuja punto por punto, `crearAlVer`); con `prefers-reduced-motion` no anima. Ficha del país: "Partido a partido" (`paises_service.obtener_balance_pais`) y curva de aficionados; ficha del jugador: radar que crece desde el centro y goles/atajadas por partido en la bitácora. Usar Chart.js con versión fija (`chart.js@4.4.4`). Macros Jinja en `templates/partials/macros.html` (`bandera`, `badge_confederacion`, `estado_vacio`): `{% import "partials/macros.html" as m %}`. La lógica de `/en-vivo` vive en `static/js/live_match.js` + `static/css/live_match.css` ("Jugadores en Cancha" arranca con el DT de cada lado —`/matches/live/plantillas` trae `dt` (quién es y su récord PREVIO; sin la amonestación/expulsión final) y `renderFilaDT` deduce ajustes, reclamos, amonestación y expulsión de los eventos ya revelados (`EventoOut` incluye `dt_id`/`dt`/`ajuste`, y `PlantillasLiveOut` el campo `dt`: los esquemas de respuesta son listas cerradas, todo campo nuevo del payload hay que agregarlo ahí)—; cola de animación de la cancha (`encolarCancha`/`pasoCola`: cada evento nuevo con `posicion_balon` o aviso se anima por separado y en orden —balón, trazo, etiqueta, fichas—, repartidos hasta el próximo poll entre `COLA_PASO_MIN_MS` y `COLA_PASO_MAX_MS`; antes solo se animaba el último de cada poll; al entrar a mitad del partido no repite la historia), accesos rápidos flotantes `#vivoAtajos` (Marcador, Cancha —solo escritorio—, Jugadores, Jugadas y Tabla —solo si `#panelTablaGrupo` está visible—; columna a la derecha en escritorio con `#panelEnVivo` dejando esa franja libre, barra abajo en celular; botón activo por IntersectionObserver); la Cancha en Vivo (`#bloqueCanchaVivo`) se oculta en celular (≤ 767px) y `canchaVisible()` evita dibujarla mientras está oculta; lista también a los que salieron de cambio o expulsados, con íconos de gol/asistencia/tarjeta/entró-salió, y marca lo que cada jugador y cada selección ocupa en /estadisticas vía `GET /matches/live/destacados` → `live_match_service.obtener_destacados_estadisticas_en_vivo`, una vez por partido; es el estado PREVIO al partido porque Estadísticas no cuenta el que se transmite); los datos que dependen del usuario llegan por `window.LIVE_CONFIG` definido en el template. `/juegos` filtra y pagina en el servidor (parámetros GET).
- **Imágenes de selección**: se sirven desde el bucket público `gs://com-icg-mundial` (`IMAGENES_PAISES_URL` en `config/settings.py`), con una carpeta por tipo (`bandera/`, `bandera_plana/`, `escudo/`, `icono/`, `jersey/`) y un archivo por país nombrado EXACTAMENTE como `paises.nombre` (`bandera/Países Bajos.png`); si se renombra un país en Mongo hay que renombrar sus archivos con `gcloud storage mv`. Tienen `Cache-Control: public, max-age=604800`, por eso la URL lleva `?v=` (`VERSION_IMAGENES` en `imagenes_pais_service.py`, replicado en `UI.urlImagenPais`/`UI.urlAvatar` vía `window.PAISES_IMG.versiones`; incluye `avatar` para `jugadores/<id>.svg`): **al regenerar un tipo, subí su versión** o los navegadores siguen mostrando la vieja una semana. `bandera/` (ondeada con relieve, fondo transparente, para usar en línea), `icono/` (circular) y `bandera_plana/` (tipo `'plana'`: a sangre, sin transparencia, SOLO para fondos con `background-size: cover` — el círculo de `.avatar-jugador`, `.goleador-fila`, las estampas) los genera `generar_banderas.py` (`--muestra`/`--generar`/`--respaldar`/`--subir`) desde flag-icons y circle-flags (MIT), resolviendo el código ISO desde el emoji de `paises.bandera`; las anteriores quedaron en `bandera_v1/` e `icono_v1/` (vuelta atrás: copiarlas encima y bajar la versión). - **Avatares de jugadores**: cada jugador tiene `jugadores.avatar_imagen` (`"jugadores/<id>.svg"`, campo PERMANENTE: `restart_mundial` solo hace `$set` de contadores) → SVG plano de FONDO TRANSPARENTE en el bucket (`jugadores/`, uno único por jugador, ~7 KB). - **Avatares de árbitros**: mismo motor (`generar_avatares_arbitros.py` hereda `Avatar` de `generar_avatares.py`), uniforme negro clásico con insignia genérica. `arbitros.avatar_imagen` (`"arbitros/<_id>.svg"`: la colección no tiene id numérico) y `arbitros.genero` (`"F"`/`"M"`, inferido del nombre: lista `MUJERES` del script, corregir ahí y volver a `--generar`/`--subir`/`--asignar`). ⚠️ `arbitros.pais_id` venía de una base vieja; `--asignar` lo reescribió con el id real resolviendo `arbitros.pais` por nombre (+ `ALIAS_PAIS`; Bahréin no está en `paises` y queda en `None`). Como los partidos solo guardan el NOMBRE del árbitro, en vistas se usa `datos_arbitro(nombre)` → `{url, pais_id}` (Jinja global) y el macro `m.avatar_arbitro(nombre, tam)`; con nombres repetidos (hay 10) gana el primero.
- **Tema visual**: `base.html` usa `data-bs-theme="dark"` (Bootstrap 5.3) con la paleta en `static/css/styles.css`. El verde de marca es `.text-accent`/`.bg-accent`/`.border-accent`; `warning` es ámbar real (advertencias, tarjetas amarillas). No volver a redefinir colores de Bootstrap (`.text-warning`, `.bg-light`, `.text-dark`) en el CSS global: usá `bg-body-tertiary`/`text-body-emphasis` para fondos y textos que deben adaptarse al tema.
- **IDs**: se usa `ObjectId` de Mongo (importado desde `bson`) para los IDs de documentos; también se usan campos `id` numéricos (por ejemplo, id de país) como referencia cruzada entre colecciones — verificá cuál espera cada función. Los campos "dueño" (`paises.user_id`, `ciudades.owner_user_id`) usan `0`/`"0"`/`None` como "sin dueño", no ausencia del campo.
- **Aleatoriedad ponderada para la simulación**: eventos de partido, clima, etc. usan `random.choices(opciones, weights=[...])` con diccionarios de opciones basados en datos en lugar de condicionales hardcodeados — seguí este patrón para nuevas mecánicas probabilísticas del juego. Para duelos entre dos jugadores/equipos, usá `resolver_duelo(prob_base, attr_atacante, attr_defensor)` (`services/simular_service.py`) en vez de inventar una fórmula nueva.
- **Scripts sueltos de una sola corrida para datos derivados/migraciones** (`asignar_rasgos_jugadores.py`, `ajuste_pais_jugador.py`, etc.): cuando un campo debe asignarse una vez y persistir para siempre (no resetearse en cada `restart_mundial`), el patrón es un script en la raíz del repo con `pymongo.UpdateOne` + `bulk_write`, corrido manualmente contra la base real — no una migración automática ni un endpoint.
