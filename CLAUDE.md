## Resumen del proyecto

**FutbolSim** ("Simulador de Fútbol") es una aplicación web FastAPI que simula un Mundial completo: clasificación de países por confederación a través de múltiples fases, sorteo de grupos, calendario de partidos, simulación realista de partidos (estadísticas a nivel de jugador, tácticas, desgaste, clima, tiros libres, córners, penales, expulsiones), rankings y un dashboard de estadísticas. Sobre ese núcleo de torneo corre una capa completa de "meta-juego"/economía para el usuario logueado: quinielas, mercado de selecciones (comprar/vender países como acciones), fantasy ("Once Ideal"), álbum de estampas coleccionables, inversión en sedes/estadios, misiones diarias + trivia, un "scouter" de pre-partido con probabilidades, popularidad/aficionados por país, y una vista de "Simulación en Vivo" que revela un partido ya simulado minuto a minuto como si fuera en directo. Renderizado en el servidor con Jinja2 + Bootstrap 5 (vía CDN) salvo la vista en vivo, que es 100% client-rendered contra endpoints JSON; MongoDB Atlas es el único datastore realmente en uso.

## Comandos

```bash
# Instalar dependencias (usar el .venv existente o crear uno)
pip install -r requirements.txt

# Levantar el servidor de desarrollo (auto-reload)
uvicorn main:app --reload
```

No hay linter, formatter ni framework de tests configurado (no hay pytest/ruff/flake8/pyproject.toml). `test.py`, `probar_calificaciones.py`, `ajuste_pais_jugador.py`, `asignar_rasgos_jugadores.py`, `configurar_juego_en_vivo.py` y `configurar_roles.py` son scripts sueltos que se ejecutan directamente con `python <archivo>.py` contra la base de datos real (para rellenar datos, volver a procesar fases de clasificación, o asignar rasgos de jugador de una sola vez) — no son una suite de tests automatizada, y varios son de una sola corrida (idempotencia no garantizada, ver comentarios de cada uno antes de repetir la ejecución). No hay paso de build; es una app server-rendered simple.

## Arquitectura

**Capas**: `routes/` (routers de FastAPI, solo HTTP + templating con Jinja2) → `services/` (toda la lógica de negocio y el acceso a MongoDB) → MongoDB (base de datos `mundial`). Las rutas deben mantenerse delgadas: parsear el request, llamar funciones de `services/`, renderizar un template. La lógica de dominio, validaciones y consultas a la base de datos van en `services/`, no en `routes/`.

- `main.py` — crea la app `FastAPI`, monta `/static`, agrega CORS permisivo y `GZipMiddleware` (respuestas > 1 KB: las páginas con listas largas, como la hoja de 840 árbitros del álbum, bajan ~10x), e incluye ~27 routers de `routes/` (varios módulos exportan un router de API y un `route_vistas` de UI por separado, bajo prefijos distintos).
- `config/settings.py` — prefijos de rutas (`PREFIX_*_PATH`) y configuración desde el entorno / `.env` (plantilla en `.env.example`, `.env` está en `.gitignore`): `MONGODB_URI` (obligatoria: la app no arranca sin ella), `SECRET_KEY` y `COOKIE_SECURE`. En Cloud Run se pasan con `gcloud run deploy ... --set-env-vars` (o `--set-secrets`). Nunca volver a escribir credenciales en el código.

### `routes/` — núcleo del torneo

`simular_route.py` (`/simulador`), `paises_route.py` (`/paises`), `jugadores_route.py` (`/jugadores`), `confederacion_route.py` (`/confederacion`), `juegos_route.py` (`/juegos`), `estadisticas_route.py` (`/estadisticas`), `home_route.py` (sin prefijo, dashboard + `/restart`). `live_match_route.py` (API `/matches`, UI `/en-vivo`) es la "Simulación en Vivo": simula y persiste el partido de una, pero expone el resultado a través de una ventana de revelación progresiva (ver sección de esquema más abajo) — la única vista que no usa Jinja para sus datos, todo llega por `fetch` contra JSON.

### `routes/` — capa de meta-juego (requiere sesión y el permiso de su sección, ver `auth_route.py` y "Roles y secciones")

Cada uno con router de API + `route_vistas` de UI bajo un prefijo de UI distinto:

- `quinielas_route.py` (API `/pools`, UI `/quinielas`) — boletos de quiniela sobre próximos partidos (LOCAL/EMPATE/VISITA).
- `ownership_route.py` (API `/ownership`, UI `/selecciones`) — comprar/vender selecciones nacionales como acciones, dividendos por victoria y avance de fase.
- `fantasy_route.py` (API `/fantasy`, UI `/once-ideal`) — armar un Once Ideal de 11 jugadores por fase, puntaje según desempeño real.
- `album_route.py` (API `/album`, UI `/album-estampas`) — comprar/abrir sobres de estampas (jugador/ciudad/país), ver colección.
- `venue_route.py` (API `/venues`, UI `/sedes`) — patrocinar ciudades sede, cobrar regalías por partido alojado.
- `rewards_route.py` (`route_rewards` en `/rewards`, `route_trivia` en `/trivia`, UI `/misiones`) — check-in diario, "beca" de rescate por bancarrota, trivia dinámica de 3 preguntas generadas desde datos reales.
- `niveles_route.py` (UI `/niveles`, sección `niveles`) — "Niveles de Socio FIFAV": página "Mi Nivel" (escalera de niveles, cómo ganar XP con el avance de hoy, logros, historial), `POST /niveles/reclamar/{n}` y `POST /niveles/visto` (cierra el aviso de subida de nivel de `base.html`).
- `corporativo_route.py` (API `/corporativos`, UI `/corporativo`, sección `corporativos`) — "Corporativos Deportivos": modo carrera como CEO de uno de 10 corporativos que representan selecciones y jugadores (ver servicios `corporativo_*` más abajo).
- `asistente_route.py` (API y UI `/asistente`, sección `asistente`) — asistente virtual "El Profe": escaneo pagado de todo lo del usuario con consejos que enlazan a cada módulo (ver `asistente_service.py`).
- `prematch_route.py` (API `/matches`, UI `/scouter`) — análisis pre-partido: estado de clasificación matemático o probabilidad Elo + veredicto narrativo.
- `fanbase_route.py` (API `/countries`, UI `/aficionados`) — ranking de popularidad/aficionados por país (independiente del ranking FIFA).
- `juego_en_vivo_route.py` (API `/live-game`, sin vista propia: la UI vive en `/juegos` — modal para elegir país — y en `/en-vivo/` — panel de juego) — "Juego en Vivo": elegir una selección de un partido pendiente pagando una entrada de `usuarios.monto`, sumar/restar puntos por cada evento revelado de la transmisión con un multiplicador de riesgo (x1/x1.5/x2/x3), y cobrar los puntos finales al terminar.
- `auth_route.py` (sin prefijo) — login/logout/cuenta y `/cuenta/password` (cambio de contraseña propio; obligatorio si `usuarios.debe_cambiar_password`). **El registro público se cerró**: las cuentas las crea un admin en `/admin/usuarios`. Después del login redirige a la primera sección que el rol puede ver (`config/secciones.py::pagina_inicial`).
- `admin_route.py` (UI `/admin`, permiso `gestion_usuarios`) — gestión de usuarios (crear con contraseña inicial o generada, editar rol/activo, restablecer contraseña), abonar puntos al saldo (`usuarios_service.abonar_puntos`: solo montos positivos, motivo obligatorio, auditado en la colección `ajustes_saldo` y visible en el historial de la cuenta como categoría "Ajuste") y de roles (matriz de permisos por sección). Lógica en `services/usuarios_service.py`, con salvaguardas: siempre queda ≥1 admin activo, un admin no se desactiva ni se quita el rol a sí mismo, el rol de sistema `admin` no se borra ni se recorta, un rol con usuarios no se borra.
- `torneo_route.py` — vistas de consulta `/cara-a-cara` (`cara_a_cara_service.py`; su `obtener_cara_a_cara` también alimenta el bloque "Enfrentamientos anteriores" `templates/partials/enfrentamientos.html` del Scouter y del detalle previo `/simulador/?id=`, con `excluir_id` para no contar el propio partido; sin selección, la portada muestra `clasicos_destacados()`), `/cuadro` (`cuadro_service.py`: llaves de fases 8-13 reconstruidas con `fase_id` + `grupo`, mismos pares que `grupos_service`) y `/palmares` (`palmares_service.py`: archivo de mundiales desde `mundiales` + finales en `juegos`).
- `/estadisticas/graficos` ("El Mundial en gráficos", `services/graficos_service.py`, enlazada desde el encabezado de /estadisticas): ~17 gráficos (Chart.js 4.4.4) del Mundial en curso: ritmo (goles acumulados + proyección con banda del 90%, media móvil, goles por franja, reparto de resultados, mapa de calor de marcadores), confederaciones, selecciones (ataque vs defensa, posesión vs puntos con r de Pearson, aficionados), jugadores (carrera de goleadores, tipo/zona/edad de los goles), estadios y clima (solo si hay ≥30 partidos con aforo) y pronósticos (próximos partidos y Monte Carlo de candidatos al título con el modelo conservador de `asistente_reglas.probabilidades_partido`). Reusa la caché de `estadisticas_service` (`_cache_vista`) y tiene la suya con la misma clave. Sistema visual en la sección `mg-*` de styles.css: paleta categórica de 8 en orden fijo (`--s1`…`--s8`, validada contra el fondo `#111c2e`), una serie = `--s1`, cada gráfico con su tabla ("Ver datos").
- Vistas de análisis agregadas después: `/arbitros` y `/arbitros/perfil?nombre=` (`arbitros_service.py`, sección `arbitros`; los partidos guardan solo el NOMBRE del árbitro), `/ranking` (`ranking_usuarios_service.py`, sección `ranking_usuarios`: patrimonio = saldo + selecciones activas + sedes), `/quinielas/rendimiento` (`quinielas_service.obtener_rendimiento_quinielas`), `/jugadores/comparar` + `/jugadores/api/buscar` (`jugador_analisis_service.py`; los números del comparador salen de los partidos del Mundial activo vía `estadisticas_service._agregar_jugadores_mundial`, no de los contadores de `jugadores`), y secciones dentro de páginas existentes: bitácora de partidos en `/jugadores/{id}` (desde `resultado.participantes`) y trayectoria por Mundial en `/paises/{id}` (`paises_service.obtener_trayectoria_pais`). `/simulador/?id=` de un partido ya jugado redirige al resumen `/juegos/{id}` (una sola vista de partido terminado; el rating por jugador solo existe en `/simulador/simular`, no se persiste). Al sumar una sección nueva al catálogo, los roles YA sembrados no la reciben solos: agregarla a mano en /admin/roles (o con `$addToSet` sobre `roles.permisos`).

`prematch_route.py` y `live_match_route.py` comparten el prefijo de API `/matches` (FastAPI permite varios `APIRouter` bajo el mismo prefijo, se distinguen por `tags` en `/docs`).

### `services/` — núcleo del torneo

- `mundial_service.py` — orquesta un torneo completo: creación de un nuevo Mundial (`crear_nuevo_mundial`), reinicio total (`restart_mundial`, ver esquema de datos), avance a la siguiente fase, agregados para el dashboard.
- `config/eliminatorias.py` — texto del encabezado del inicio por (confederación, fase) y rondas por confederación (`RONDAS_POR_CONFEDERACION`, el "Ronda X de N"); refleja las reglas de `clasificacion_service.py`, si cambia un formato allá hay que actualizar el texto acá.
- `confederacion_service.py`, `clasificacion_service.py` — lógica de clasificación por confederación (`get_confederacion` + `_enriquecer_vista_confederacion` arman la vista `/confederacion/{id}`: tabla de cada grupo ya ordenada con racha de 5 y estado avanzó/en juego/eliminado, avance por ronda, descripción del formato desde `config/eliminatorias.py`, últimos/próximos partidos — una sola consulta de `juegos` con proyección); `clasificacion_service.py` tiene funciones por fase (`procesar_clasificacion_fase_1` … `_7`, más una genérica) ya que el formato de clasificación difiere entre confederaciones, y `obtener_tablas_posiciones_por_grupo`/`obtener_tabla_grupo_de_equipo` (reusadas por `prematch_service.py` y `live_match_service.py`).
- `grupos_service.py` — sorteo de grupos para cada etapa eliminatoria.
- `juegos_service.py` — ciclo de vida del partido: generación de fixtures, `ejecutar_simulacion_completa` (motor + persistencia + efectos secundarios, compartido por `simular_route.py` y `live_match_route.py`), asistencia (`calcular_asistencia`), clima (`generar_clima_partido`).
- `simular_service.py` — el motor de simulación (`simular_partido_realista`): posesión por zona (`defensa`/`medio`/`ataque`) con duelos de atributos vía `resolver_duelo` (probabilidad tipo Elo sesgada por diferencia de atributos), y sub-motores dedicados para penales (`ejecutar_penal` + tanda completa en `simular_tanda_penaltis`), tiros libres directos (`ejecutar_tiro_libre`, cadena muro→a puerta→arquero) y córners (`ejecutar_corner`, cadena disputa aérea→a puerta→arquero) — los tres últimos agregados recientemente, junto con `bonus_pie_habil` (plus de precisión para jugadores `pie_habil == "ambidiestro"`) y bonos de `especialista_penales`/`especialista_tiros_libres` en sus respectivos duelos. **Desgaste físico** (`services/desgaste.py`, lógica pura): cada jugador entra con 100 de energía, que baja con el tiempo jugado (`GASTO_POR_MINUTO`; el arquero igual: su desgaste es de concentración y reflejos) y con cada acción que protagoniza o defiende (`COSTO_ACCION`), frenado por su `resistencia` y acelerado por el clima (`modificadores.desgaste` de `generar_clima_partido`); por debajo de 70 sus atributos rinden menos (hasta 10%, los defensivos hasta 38%: el cansancio abre los partidos; calibrado con Monte Carlo para que los goles por partido no cambien) — los valores sin cansancio quedan en `jugador['_base']` y los atributos del dict del partido se reescriben en el lugar, así todos los duelos lo sienten sin tocar cada fórmula. Los cambios priorizan a los más cansados (`desgaste.peso_para_salir`), la probabilidad de cambio sube con el cansancio (`PROB_CAMBIO_BASE`/`PROB_CAMBIO_POR_CANSANCIO`/`UMBRAL_CAMBIO_ENERGIA`) y el que entra llega fresco; al cruzar 30 de energía se narra un evento `🥵 DESGASTE`; `stats_jugadores[id].energia_final`. También modela tarjetas/expulsiones (`procesar_expulsion`, saca al jugador de `plantilla` en tiempo real y lo excluye de la posesión inmediatamente), sustituciones (`realizar_sustitucion`), clima/árbitros y alargue + penales para series ida-vuelta.
- `paises_service.py` / `international_service.py` — datos de países, poder y ranking (`actualizar_poder_y_rankin`, `recalcular_rankin`).
- `jugadores_service.py` — `actualizar_jugadores_post_partido` es el único punto que persiste stats de partido en la colección `jugadores` (ver "Esquema de datos" para la lista completa de campos `$inc`).
- `ciudades_service.py`, `fecha_service.py`, `estadisticas_service.py` — ciudades sede, calendario y agregación de estadísticas para el dashboard (**todo del Mundial en curso**: `_filtro_finalizados()` agrega `mundial_id` activo y excluye el partido en transmisión a todas las consultas; `obtener_estadisticas_generales` carga una sola vez los partidos con proyección (`_juegos_del_mundial`), arma por jugador `_agregar_jugadores_mundial` (goles/atajadas/participantes del resultado + asistencias, tarjetas, faltas, recuperaciones, regates y disparos desde los eventos, resolviendo nombre→id por (país, nombre); los contadores de `jugadores` NO sirven porque no se reinician entre mundiales) y por selección `_agregar_paises_mundial`, de ahí salen los líderes y los top 10 (`TOP_JUGADORES`/`TOP_SELECCIONES`); el resultado se cachea en memoria con clave (mundial, cantidad de partidos jugados), así solo se recalcula cuando termina un partido; `GET /estadisticas/api/detalle?tipo=jugador|seleccion&id=&metrica=` (`obtener_detalle_estadistica`) da los partidos donde sumó cada uno para el modal; `estadisticas_service.py` ya tiene ~15 líderes distintos, más récords por partido derivados de `resultado.eventos` — árbitro central con más/menos faltas y tarjetas EN UN partido (no promedio: cada central dirige 1-4 partidos), primer gol más rápido/tardío, sede más goleadora — y un bloque de tendencias del torneo (goles/partido, ambos marcan, localía, goles por franja, mayor goleada, hat-tricks), todo desde una sola consulta con proyección (`_juegos_finalizados_para_records`); varios requieren recorrer `juegos.resultado.goleadores[]`/`eventos[]` de todo el torneo en vez de un simple `find_one` sobre `jugadores`, ver esquema).
- `live_match_service.py` — motor de la "Simulación en Vivo": simula y persiste el partido de una, pero lo expone a través de una máquina de estados `juegos.transmision` (`in_progress`/`finished`) que revela `resultado.eventos` progresivamente según el tiempo transcurrido real. Los efectos secundarios (país, jugadores, rankings, aficionados, quinielas, ownership, fantasy, sedes, avance de fase) quedan diferidos en `juegos.efectos_pendientes` hasta que la ventana termina, para no spoilear standings/perfiles antes de tiempo — `obtener_estado_live` hace un "auto-finalize-on-read" con update condicional atómico sobre `transmision.estado`, así que aunque varios clientes hagan polling a la vez los efectos se disparan exactamente una vez.

### `services/` — capa de meta-juego y soporte

- `album_service.py` — (vista HTML del álbum: `obtener_album_pagina`, un álbum de 212 páginas —una por país, ordenadas por confederación, con TODOS los casilleros de cada país: escudo, ciudades sede y plantel; y la 212, la página especial de árbitros: 840 estampas **Doradas** en pestañas por puesto (`PUESTOS_ARBITRO`)—; **categorías de rareza** en `CATEGORIAS_ESTAMPA` (única fuente de verdad: de ahí salen `PESOS_TIPO_ESTAMPA`, `BONUS_DUPLICADA_POR_TIPO`, la XP por categoría `ACCION_XP_POR_TIPO` y los marcos `estampa--{normal,especial,dorada,platino}` de `album.css`): Normal = jugador 59% (repetida 10 pts), Especial = estadio 20% (15), Foto de equipo 6% (20, ver "Fotos de equipo"), Leyenda 5% (25), Dorada = árbitro 7% (30), Platino = escudo 3% (50); `_elegir_tipo_estampa` sortea con esos pesos y el Sobre Platino de las recompensas de nivel trae un escudo garantizado; cada estampa del sobre lleva `categoria` en la respuesta; se arma una sola página por pedido y `/album-estampas/coleccion/pagina/{n}` devuelve la hoja suelta (`templates/partials/album_pagina.html`) para hojear sin recargar, `?pagina=`/`?pais=` abren directo; el catálogo fijo (países y a qué país pertenece cada jugador/ciudad) se cachea en memoria; estampas con frente/reverso en `templates/partials/estampas.html` + `static/css/album.css`, que también usa la animación de `album_sobres.html`; `buy_and_open_pack` devuelve además el detalle de cada estampa vía `_detallar_estampas`, solo en la respuesta, no en `pack_purchases`) el **hub de sinergia** del juego: `user_albums` (arrays `owned_jugadores`/`owned_paises`/`owned_ciudades`) es leído por `ownership_service.py`, `venue_service.py` y `fantasy_service.py` para dar bonos a quien tenga la estampa correspondiente (ver "Convenciones" más abajo). `album_service.py` en sí solo vende sobres y arma la vista de colección — no calcula sinergia, solo la refleja leyendo las marcas (`album_synergy_applied`, `sinergia_album_aplicada`, `SINERGIA_ALBUM`) que cada módulo sinérgico deja en su propia colección de transacciones.
- `ownership_service.py` — mercado de selecciones (`team_ownerships`/`ownership_transactions`), dividendos por victoria y bono de avance de fase (las vistas usan `obtener_mercado_vista`/`obtener_portafolio_vista`: contexto deportivo por país con `_contexto_paises` —estado en el Mundial, ranking, récord, próximo partido—, variación del valor, sinergia de álbum, resumen y últimos movimientos), con sinergia de álbum (×1.5 al dueño si tiene la estampa del país, +20 pasivo a cualquier otro que la tenga).
- `venue_service.py` — mercado de sedes/ciudades (`city_ownerships`/`city_revenue_history`), regalías por partido alojado, misma sinergia de álbum (×1.5 / +20 pasivo) sobre estampas de ciudad.
- `fantasy_service.py` — Once Ideal (`fantasy_teams`/`fantasy_points_history`): **UN equipo por usuario y Mundial** (`{user_id, mundial_id}`; ya no por fase: cada confederación avanza a su ritmo y las fases se intercalan en el calendario) que suma en TODOS los partidos del Mundial (`procesar_eventos_jugadores_partido(..., mundial_id)`). Los cambios se liberan por **jornada fantasy** (`jornada_actual()`: cada `PARTIDOS_POR_JORNADA` = 20 partidos jugados del Mundial): +`CAMBIOS_GRATIS_POR_JORNADA` (2) acumulables hasta `TOPE_CAMBIOS_GRATIS` (5), acreditados al leer (`_equipo_del_mundial`, campo `jornada_credito`); cada cambio extra cuesta `COSTO_CAMBIO_EXTRA` (20) de saldo (`calcular_cambios` arma el desglose; el modal de `/once-ideal` lo replica en JS). Jugadores de selecciones eliminadas o que no juegan el Mundial (`paises_eliminados()`: `internacional.estado` ELIMINADO_* o ausente) se marcan, no suman, no se pueden agregar y reemplazarlos es gratis. `_equipo_del_mundial` migra solo los equipos viejos por fase (fusiona en el de fase más alta, suma los puntos y borra el resto). Puntaje por desempeño real de cada jugador, sinergia de álbum de tres vías: solo en el equipo (100%), solo la estampa sin lineup (20% pasivo, va a `usuarios.monto` vía `album_passive_rewards`, no es puntaje fantasy), o ambos (×1.5, 150%).
- `quinielas_service.py` — boletos de quiniela (`quiniela_config`/`quiniela_usuario`), liquidación automática al terminar cada partido. Sin sinergia de álbum.
- `fanbase_service.py` — aficionados/popularidad por país (`paises.aficionados`, historial en `historial_aficionados`), con "efecto estrella" y multiplicador David-vs-Goliat. Sin sinergia de álbum.
- `rewards_service.py` / `trivia_service.py` — (la vista `/misiones` sale de `obtener_misiones_vista`: checklist del día `MISIONES_DEL_DIA` con la XP de hoy por acción y filtrado por permisos, racha vigente —la guardada se corta si el último check-in no fue hoy ni ayer—, cupos y estadísticas de trivia, requisitos de la beca uno por uno y últimos premios; la trivia se juega en un modal, una pregunta a la vez) check-in diario y beca de rescate por bancarrota (`user_daily_rewards`/`reward_transactions`), y trivia dinámica de 3 preguntas por sesión generada en vivo desde 5 colecciones reales (`trivia_history` guarda la respuesta correcta server-side, nunca se manda al cliente).
- `juego_en_vivo_service.py` (Mongo) + `juego_en_vivo_puntos.py` (lógica pura: reglas, multiplicador vigente, tope en 0, cooldown, resumen) — Juego en Vivo. Valores por defecto en `config/juego_en_vivo.py` (entrada, cuotas por favoritismo, niveles de riesgo, cooldown, reglas de puntos — calibradas con Monte Carlo para que x1 quede ~neutral). Los puntos se procesan **al leer** (cada poll de `GET /live-game/state`): no hay WebSockets/SSE ni tareas en segundo plano, y Change Streams no sirven porque los eventos no se escriben de a uno (ver `live_match_service.py`). Reglas clave: cada evento usa el multiplicador vigente en su **instante de revelación** (`live_match_service.instante_revelacion_evento`, determinístico), un cambio de riesgo durante la transmisión entra en vigor 10 s después (anti "ver el ⏳ PREPARACIÓN y subir el riesgo") con cooldown de 60 s liberado por gol, y las reglas de resultado se evalúan con el ÚLTIMO evento del partido (no con el pitido: la tanda de penales se narra después). Cada lote se guarda en una transacción de Mongo con compare-and-set sobre `ultimo_evento_procesado`. ⚠️ Como el procesamiento es al leer, una sesión cuyo dueño se fue de `/en-vivo` quedaba abierta para siempre (entrada cobrada, sin pago): ahora `liquidar_sesiones_abiertas` cierra las sesiones de partidos ya terminados, y se llama al terminar cada transmisión (`live_match_service._disparar_efectos_pendientes`, para todos los usuarios de ese partido) y en cada `obtener_estado_juego` (para el usuario).

Scouting (`corp_scouting`, uno por ciclo) y marketing (+reputación, uno por ciclo). ## Esquema de datos (MongoDB, base `mundial`)

La base tiene ~25 colecciones. Núcleo del torneo:

- **`paises`** (211 docs) — roster maestro y permanente de selecciones (nombre, confederación, `estadisticas` anidadas, `rankin`, `poder`, `aficionados`). Además de esto persiste `user_id` (0/`"0"`/`None` = sin dueño, ver `ownership_service.py`) para el mercado de selecciones. Persiste entre mundiales.
- **`internacional`** (197 docs) — snapshot de un país **para el mundial activo**: mismos campos que `paises` más `mundial_id`, `fase_eliminatoria`, `grupo`, `idx_grupo`, `eliminado`.
- **`historial`** (28 docs) — mismo shape que `internacional`; archivo de instancias de mundial ya finalizadas.
- **`grupos`** (9 docs) — snapshot de cada grupo al momento del sorteo. ⚠️ Los países acá guardan las estadísticas **planas** (`puntos`, `jj`, `jg`, `je`, `jp`, `gf`, `gc` directo en el doc) en vez de anidadas bajo `estadisticas` como en `paises`/`internacional`.
- **`juegos`** (878+ docs) — un partido: `equipo_local`/`equipo_visitante`, `ubicacion`, `estadisticas.{local,visitante}` (incluye `tiros_totales` por lado, agregado para la efectividad de gol real por país), y `resultado` (goles, árbitros, `eventos[]`, `opinion`, `ganador_id`/`ganador_lado`/`empate`) que solo existe una vez simulado. `resultado.goleadores[]` es la lista estructurada de quién anotó, con flags adicionales por entrada: `entro_de_cambio` (Súper Sub), `equipo`, `goles_penal`/`goles_tiro_libre`/`goles_corner` (para "Especialista a Balón Parado" — desglosan de qué tipo de jugada vino cada gol; **no** se acumulan en `jugadores`, solo viven acá, así se resetean solos en cada `restart_mundial`). `resultado.atajadores[]`/`resultado.participantes[]` análogos, para racha de goles y modal de "ver partidos". `aforo`/`clima` se agregan post-simulación. `transmision` (`estado: in_progress/finished`, `started_at`, `duracion_segundos`) y `efectos_pendientes` son campos aditivos que solo existen si el partido pasó por el flujo de "Simulación en Vivo" (ver `live_match_service.py`).
- **`jugadores`** (~6963 docs; **33 por selección: 22 actuales —2 por cada una de las 11 posiciones— + 11 LEYENDAS**) — `nombre`/`edad` actualizados con futbolistas reales en actividad por `actualizar_jugadores_reales.py` (Wikipedia: plantel actual + convocatorias recientes, posición exacta de la ficha de cada jugador; `--descargar`/`--muestra`/`--aplicar`/`--revertir`, y `--renombrar "id=Nombre:edad"` para cambios puntuales a mano por el mismo camino; respaldo en `respaldos/`). ⚠️ El NOMBRE del jugador también vive en los partidos jugados (`resultado.eventos[].jugadores`/`descripcion`, `goleadores`/`atajadores[].jugador_nombre`, `comentarios_jugadores`, `titulares_*`, `opinion`, `texto_narrativo`) y en `fantasy_points_history.jugador_nombre`, y Estadísticas vincula eventos por (país, nombre): si renombrás jugadores, reescribí también esas referencias (el script lo hace) o el Mundial en curso pierde sus números. Atributos de simulación (`overall`, `precision_tiro`, `regate`, etc.) y contadores de carrera **por torneo** (se resetean en cada `restart_mundial`, no son acumulado histórico — pese a lo que sugeriría el nombre; el código documenta explícitamente que los campos `_temp` que alguna vez existieron para separar "este torneo" de "histórico" fueron eliminados por no usarse). Contadores actuales, todos `$inc`-eados en `jugadores_service.actualizar_jugadores_post_partido`: `goles`, `asistencias`, `atajadas`, `faltas`, `amarilla`, `roja`, `tiros_puerta`, `tiros_desviados`, `faltas_recibidas` (faltas RECIBIDAS, distinto de `faltas` cometidas), `recuperaciones`, `atajadas_penales` (subconjunto de `atajadas`, específicamente en penales), `juegos_jugados`. Campos **permanentes** (ya NO se resetean en restart, ver `mundial_service.py::restart_mundial`, asignados una sola vez por `asignar_rasgos_jugadores.py`): `pie_habil` (`"derecho"`/`"izquierdo"`/`"ambidiestro"`, distribución ~78/18/4%, afecta duelos de tiro vía `bonus_pie_habil` en `simular_service.py`) y `especialista_penales`/`especialista_tiros_libres` (booleans, ~55% de los equipos tiene uno marcado por rol, dan un bono de precisión en sus respectivos duelos y prioridad para cobrar). **Leyendas** (`leyenda: true`, `agregar_leyendas.py` `--descargar`/`--muestra`/`--aplicar`/`--revertir`; once histórico de retirados por país desde Wikidata + fichas de Wikipedia + `leyendas_curadas.json`; ids desde 4643, dorsales 23-33, edad de plenitud, atributos 80 parejo para todos los países —paridad—, `atributos_base` (lo que restaura `restart_mundial` en vez de 60), `fama` 0..1 (percentil entre leyendas, para el precio), `wikis` (cantidad de Wikipedias con artículo) y `wikidata`; evolucionan partido a partido como cualquiera. ⚠️ Cualquier código que lea `jugadores` tiene que decidir si incluye leyendas: el álbum las tiene como categoría propia `LEYENDA` (5%, guardadas en el mismo `owned_jugadores`, sección aparte en la página del país que NO cuenta para completarla), corporativos las valúa con escala propia (`corporativo_reglas.valores_con_leyendas`: el percentil de los actuales se calcula SIN ellas) y arrancan libres (la siembra las excluye; Macro `m.insignia_leyenda()`. ⚠️ Sigue teniendo el par redundante `control_balón` (con tilde, huérfano/muerto) vs `control_balon` (sin tilde, el que se lee de verdad) — verificar cuál usa cada función antes de tocarlo.

Índices y reglas se crean con `python configurar_juego_en_vivo.py` (idempotente).

- **`dos_equipos`…`diez_equipos`** — tablas de fixture-template que mapean qué posición de grupo enfrenta a cuál en cada jornada, según el tamaño del grupo.
- **`usuarios`** — cuenta del jugador humano (`monto` = saldo gastable, hasheo bcrypt, `rol` = código de la colección `roles`, `debe_cambiar_password`, `activo` = interruptor de acceso). **`roles`** — `{codigo (único), nombre, descripcion, permisos: [códigos de config/secciones.py] o ["*"], es_sistema}`; se siembran con `python configurar_roles.py` (idempotente; `--password-admin` fija la contraseña de `dummy`, el admin inicial). `restart_mundial` solo resetea `monto`, no toca roles. Todo el resto de colecciones de meta-juego cuelgan de `usuarios` vía `user_id`/`ObjectId`: `user_albums` (`owned_jugadores`/`owned_paises`/`owned_ciudades`/`owned_arbitros`, listas de `id` numérico; `arbitros.id` es PERMANENTE, asignado por `asignar_id_arbitros.py`, índice único en `crear_indices.py`), `pack_purchases` (álbum); `team_ownerships`, `ownership_transactions` (selecciones); `city_ownerships`, `city_revenue_history` (sedes); `fantasy_teams`, `fantasy_points_history`, `album_passive_rewards` (fantasy); `quiniela_config`, `quiniela_usuario` (quinielas); `user_daily_rewards`, `reward_transactions`, `trivia_history` (misiones/trivia); `historial_aficionados` (aficionados); `match_live_sessions`, `point_transactions` (Juego en Vivo); `xp_eventos`, `recompensas_nivel` (niveles, permanentes).

Esquema completo por colección (todos los campos y tipos) relevado con `ver_esquema.py` (script de solo lectura, no forma parte del flujo de la app).

## Convenciones y patrones

- **Vocabulario de dominio en español** en todo el proyecto (routes, services, variables, templates): `pais`/`paises`, `juego`/`partido`, `fase`, `confederacion`, `mundial`, `clasificacion`, `rankin` (ranking/poder), `plantilla` (squad). Mantené el código nuevo consistente con este vocabulario — no mezclar términos de dominio en inglés.
- **Sinergia del Álbum de Estampas**: patrón repetido en `ownership_service.py`, `venue_service.py` y `fantasy_service.py` — cada uno consulta `user_albums.owned_paises`/`owned_ciudades`/`owned_jugadores` en su propio punto de pago único (`_abonar_puntos_dueno`, `process_match_city_revenue`, `procesar_eventos_jugadores_partido`) para: (a) multiplicar ×1.5 el pago al dueño/titular si además tiene la estampa correspondiente, y (b) dar un bono pasivo fijo (+20 pts, o 20% en fantasy) a cualquier OTRO usuario que tenga esa estampa, sin ser el dueño. Cada módulo deja su propia marca de auditoría (`album_synergy_applied`, `sinergia_album_aplicada`, `type == "SINERGIA_ALBUM"`) en su colección de transacciones — `album_service.py` solo LEE esas marcas para la vista de colección, nunca calcula sinergia por sí mismo. Si agregás un módulo nuevo con estampas de por medio, seguí este mismo patrón en vez de centralizarlo en `album_service.py`.
- **Efectos diferidos + revelación progresiva** (`live_match_service.py`): cuando un partido se simula vía "Simulación en Vivo", el resultado se persiste al instante pero los efectos secundarios (stats de país/jugador, rankings, dividendos, sinergias, avance de fase) quedan guardados en `juegos.efectos_pendientes` y NO se aplican hasta que termina la ventana de revelación — evita que el dashboard/perfiles spoileen el resultado antes de tiempo. Si agregás un efecto secundario nuevo a `ejecutar_simulacion_completa`, verificá si también necesita pasar por este mecanismo de diferido.
- **Conexión a la base de datos por módulo**: la mayoría de los archivos en `services/*.py` instancian su propio `MongoClient` / `db = client.get_database('mundial')` a nivel de módulo (algunos importando `MONGODB_URI` desde `config.settings`, otros redeclarando la URI inline) en lugar de compartir un único cliente. Seguí el patrón existente por archivo salvo que se pida explícitamente refactorizarlo.
- **Convención ruta → service**: las rutas arman un diccionario de contexto para Jinja y retornan `templates.TemplateResponse(request=request, name="<template>.html", context={...})`; cada módulo de rutas define su propio router (`route`, y a veces `route_vistas` separado para las páginas HTML bajo otro prefijo), un `tag` a nivel de módulo, y su propio `logging.basicConfig`/`logger`.
- **Roles y secciones**: cada vista/acción es un código de `config/secciones.py`. Al agregar una vista nueva: sumá su código (y su URL en `URL_SECCION`), protegé su router en `main.py` con `dependencies=_permiso("codigo")`, y mostrá su link en `base.html` con `{% if puede('codigo') %}` (y `nav_activo(...)` para el resaltado). Las acciones sensibles (simular, reiniciar) llevan además `Depends(requiere_permiso(...))` en la propia ruta y sus botones se ocultan con `puede(...)`. Los endpoints de escritura usan SIEMPRE el usuario de la sesión, nunca un `usuario_id` del body.
- **Frontend compartido**: `static/js/ui.js` (cargado en `base.html`) expone `UI.escapar` (usarlo SIEMPRE al meter datos en `innerHTML`), `UI.confirmar({...})` (modal propio; no usar `confirm()` nativo), `UI.refrescarSaldo()` (actualiza la pill de saldo del navbar tras una compra/venta, vía `GET /cuenta/saldo`), `UI.paginador({...})` ("Mostrar más" para listas largas renderizadas en el servidor), `UI.cargando(promesa)` y hace accesibles por teclado los elementos `role="button"`. **Indicadores de carga globales** (también en `ui.js`, sin tocar cada vista): barra de progreso arriba al hacer clic en un link interno o enviar un formulario (salvo que su handler haga `preventDefault`, o con `data-sin-cargador`), aviso "Abriendo …" con una pelota si la navegación pasa de 700 ms, y barra en todo `fetch` que tarde más de 400 ms; los polls periódicos están excluidos en `SIN_CARGADOR` (si agregás un poll nuevo, sumalo ahí). **Login animado**: `templates/login.html` envía con fetch y cabecera `X-Login-Ajax: 1` (`auth_route.login_submit` responde JSON y setea la misma cookie); acierto = animación de gol y después navega, error = atajada + mensaje; sin JavaScript o con `prefers-reduced-motion` funciona sin animación. Macros Jinja en `templates/partials/macros.html` (`bandera`, `badge_confederacion`, `estado_vacio`): `{% import "partials/macros.html" as m %}`. La lógica de `/en-vivo` vive en `static/js/live_match.js` + `static/css/live_match.css`; los datos que dependen del usuario llegan por `window.LIVE_CONFIG` definido en el template. `/juegos` filtra y pagina en el servidor (parámetros GET).
